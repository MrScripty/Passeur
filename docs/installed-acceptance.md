# Installed-host acceptance procedure

This is an opt-in operator procedure. Fixture creation, personal Codex registration, inference allowance, approval decisions and resource retirement require their respective authority. Use an isolated disposable repository for model execution, not product-development work.

1. Record Passeur build ID, Node/Git/Codex/Muse and SDK versions, model ID, OS/filesystem, profile/state binding, effective host restrictions and evidence owner. Distinguish operator subscription confirmation from billing proof.
2. Run `npm run probe:installed -- create --fixture /absolute/new-fixture --yes`. The parent directory must already exist. This creates a new Git fixture with a nonce and fixture-local identity/hook/signing settings; it does not launch inference. Retain the command's base/ref/assignment output.
3. Build/install the selected runtime and create an explicitly named fixture registration. Capture configuration and direct transport results. In a **new actual Codex session**, list the namespace and the current eleven tools and call `passeur_status`, then explicitly `passeur_prepare`. A direct SDK client does not satisfy this step.
4. Through Codex, send the generated assignment to `delegate_to_muse`. Record the real request/result and actual selected Muse runtime/model observations. Verify the returned task commit with `npm run probe:installed -- verify --fixture /absolute/new-fixture --commit FULL_TASK_OID`. This command proves only observed Git content, not who produced it or whether approvals/sandbox/billing worked.
5. Use `muse_result` to read retained evidence. Exercise a pair of independent bounded tasks through the same installed path, plus one explicitly allowed and one denied human approval and cancellation. Record actual terminal worker-stop/resource outcomes; a requested cancellation is not proof of process termination. Reuse existing parallel acceptance only where the same boundary was actually exercised.
6. Safely account for every created task worktree/ref and fixture. Preserve exact heads in retained/archive refs before removing owned resources. Record retained resources with owner/purpose/next disposition. Do not prune unrelated worktrees.
7. With explicit authority, verify actual `passeur_pumas` and `passeur_tuldok` attachment, identities, state bindings and preparation. No product inference is required. Genuine contention must be observed and resolved through safe known-owner handover, never lock deletion.

Attach redacted transcripts/receipts, actual commands and results to the plan's implementation evidence. Mark A8–A10 satisfied only for the boundaries actually observed. Missing accounts or host access leaves those claims blocked; the fixture helper, tests or a build cannot supply them.
