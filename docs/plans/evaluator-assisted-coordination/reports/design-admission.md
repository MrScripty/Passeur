# Composed-design admission

Applicability: **applicable**. These are the current eight Architecture probe answers for the complete evaluator-assisted artifact. Structural correctness, semantic advice, coordination authority and native execution have separate contracts.

## 1. Independent concerns and their dimensions

Execution supervision owns what happens to an admitted native assignment, its authenticated control principal, native lifecycle mechanisms, stopping/finalization evidence, resource location and safe lifetime. Existing Coordinator/TaskControls/adapters remain its owners.

Structural observation owns exact captured syntax, source/task attribution, native parsing, current-observation ordering, source ranges and bounded factual reports. It has no evaluator key or code-writing authority.

Evaluation owns a narrow probabilistic judgment over a fixed evidence packet, who authorized disclosure/use, the qualified provider/question/rubric, request lifetime and cost, remote endpoint and retained result, and whether the advice adds coordination value. EvaluationOwner contains that work; it does not define product requirements or native task state.

Coordination control owns work registration, attributed notes, explicit acknowledgments and reconciliation leadership. Parents own interpretation, instructions, task decomposition, verification and integration. Git owns committed source versions. Persistence owns publication/receipt mechanisms. Transport owns decoded representations and connection waits.

## 2. Required interleavings and distinct authority

Required: structural output is bound to captured bytes; evaluator output is bound to those inputs plus model/question/context/qualification identity; egress is checked against every included source; cost reservation precedes dispatch; delayed results are classified before delivery; case leadership and task control remain generation-checked at their respective owners.

Keep distinct: confidence and authorization; probability and measured accuracy; source observation and semantic hypothesis; cached result and current permission; parent notification and worker instruction; provider timeout and native task cancellation; budget window and ownership lifetime. Native evidence is never reconstructed from model scores.

No transitive semantic dependency graph or generated explanation owns behavior. A typed outcome carries closed advice only. Version roles are explicit: Git OID/capture digest, parser/extractor, model/provider contract, question/rubric, context/egress policy, qualification, control/IPC schema, and native run generation. A single release does not make their evolution one promise.

## 3. Caller and composition-root knowledge

A parent supplies its normal assignment, optional watches and source-sharing preferences. It may retrieve a report and separately labeled advice. It need not author scoring prompts, operate parser handles, choose thresholds on every task, or ask workers for routine explanations. It remains responsible for interpreting advice and directing its workers.

The composition root binds the existing runtime, structural helper, coordination store, evaluator owner, approved provider configuration and public projections. It does not know per-language syntax nodes, question-specific thresholds, persisted record layouts or remote model internals. Parser processes and native workers receive no evaluator credentials.

Disabling evaluation removes provider requirements from the normal structural path. It does not claim the full assisted objective succeeded. The installed capability matrix states the actual mode, qualification and reason when a particular assessment is unavailable.

## 4. Representative change paths and forced owners

| Representative change | Semantically forced owners |
|---|---|
| Kotlin parameter syntax evolves | Grammar/extractor/query, source fixtures and bundle manifest; relevant evaluator code-form qualification if packets change |
| Source byte-range encoding changes | Capture and parser boundary, report schema, source-span consumers and evaluator packet projection |
| EQ02 question or criteria changes | Question catalog, qualification and evaluator policy; no native task protocol rewrite |
| Provider response format changes | Provider adapter/decoder, external contract fixtures, installed SDK identity and affected model qualification |
| Parent disclosure policy changes | Authorization/context owner, stored policy version and current read/dispatch checks; no parser grammar change |
| Model verdict cache invalidation changes | Evaluation owner/store and exact-context tests; structural report identity remains separate |
| Reconciliation handoff changes | Coordination authorization/persistence/CLI presentation; evaluator does not gain claim authority |
| Native worker stop evidence changes | Existing execution lifecycle family; evaluation remains an independent observer |

Changing a model or policy requires requalification for changed meaning, not a new parser implementation. A semantically unchanged documentation correction does not invalidate a fixed evaluated subject merely by changing file timestamp.

## 5. Stable interfaces and exposed obligations

Structural consumers receive immutable capture/extraction/report representations with truthful coverage, not native tree handles. Evaluator receives a bounded authorized packet and fixed question references, not arbitrary workspace access. A provider adapter returns a validated typed result with exact model and usage; it cannot directly send a parent notice.

Evaluation policy sees distributions, missing-context facts and qualification, not raw HTTP retry internals. Notice delivery sees authorized immutable facts/advice and recipient IDs selected from existing scope. Coordination consumers see typed revisioned operations, not aggregate JSON layout. Reuse transport framing without making unrelated schemas share one semantic version.

Material limitations remain visible: approximate semantic judgment, unknown program context, unqualified language, host notification limits, uncertain remote execution/billing, and non-atomic cross-owner effects. Hiding these would increase caller reasoning rather than reduce it.

## 6. Independent evolution, failure and verification

Parser failure makes structural coverage incomplete. Evaluator failure makes advice unavailable. Neither kills an accepted coding worker. Missing disclosure blocks evaluation, not task completion. Native uncertainty preserves resources through the existing execution owner. Missing initialized coordination/evaluation authority refuses dependent mutation; a rebuildable index is not a substitute for it.

Language extraction is verified without models. Provider decoding is verified with independently specified HTTP peers. Semantic usefulness is verified against independent held-out labels using the actual model. Cost/privacy/notice effects are verified at actual process/transport boundaries. These are complementary claims, not substitutes for each other.

A future provider can replace its adapter when its real contract and workload qualify. It cannot inherit thresholds or data permissions automatically. Persisted records retain their source versions. Evaluation is a module inside the same service, not another daemon or worker-orchestration engine.

## 7. Deletion test

| Permanent mechanism | Consequence of deletion | Admission |
|---|---|---|
| Exact source endpoint/capture roles | Parents and evaluator cannot know which versions evidence describes | Retain |
| Native parser helper and per-language extraction | Required compact accurate structural report cannot be produced; work would leak to parents | Retain with language qualification |
| Parser manifest/range mapping | Source/query/ABI drift and embedded ranges become untraceable | Retain one build-owned authority |
| Conservative correspondence | Differences may be attributed to the wrong declaration | Retain syntax-only evidence/ambiguity |
| Work/notes/case control | Direct host activity and cross-parent ownership cannot be coordinated reliably | Retain small atomic records |
| EvaluationOwner/provider boundary | Authorized semantic assessment, budgets and unknown outcomes would leak into transport/parents | Retain for the admitted assisted objective |
| Fixed question/rubric catalog | Arbitrary caller prompts could change meaning without versioning or qualification | Retain closed product questions |
| Context/disclosure projection | Paid requests could use wrong, excessive or unauthorized source | Retain at the external data boundary |
| Qualification record and independent corpus | Probabilities would be promoted to useful advice without workload evidence | Retain; no general benchmark platform |
| Cache/single-flight policy | Repeated unchanged observations can duplicate paid work | Retain only exact identity and bounded cache needed by the cost claim |
| Evaluation accounting/receipt aggregate | Concurrent budgets and crash recovery lose paid-call state | Retain separate small atomic authority; not another task store |
| Deterministic notice lane | A wrong or missing model answer can suppress required factual/control information | Retain independently of scoring |

No generic plugin bus, automatic repair agent, model-written source plan, generated prose engine, compiler resolver or target publisher is introduced.

## 8. Necessary complexity and complete artifact

The artifact retains one repository service and native scheduler, one initial parser helper, bounded coordination control, and one evaluator owner using the approved provider. Its inherent additional cost is context policy, paid-call accounting, probabilistic qualification and separated advice delivery. Those obligations are justified only by the admitted intent/relevance/interaction/agreement decisions and measured benefit to parents.

The complete design can run deterministically when the evaluator is disabled, but full assisted acceptance also requires real model quality and cost evidence. A missing or poor model is not hidden by a successful structural report. Re-run admission if implementation starts requiring broad semantic state, model-selected filesystem access, automatic instructions, extra daemons or materially wider coupling than these change paths.
