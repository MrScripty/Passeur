# Language and parser qualification

This matrix is the required SC04 acceptance population. It refines D4–D6; it does not authorize reducing the population to the grammars easiest to install. All rows are **pending**. No parser packages have been installed or extraction tests executed while writing this plan.

## 1. Common contract and support boundary

For each row, prove declaration-kind/name and enclosing-syntax extraction, ordered parameter/pattern components, written type and result syntax where present, modifiers that are part of that declaration, direct type/member edits, and body-only or non-declaration changes. Distinguish `not_declared` from unavailable extraction. Matching must handle repeated names and additions/removals without silently claiming semantic identity.

The support record names the modern language edition/version/features actually admitted, full grammar source commit, runtime binding identity, generated artifact digest, scanner/build dependencies, query/extractor identity, supported ABI, license/notice obligations, and exact positive/negative fixtures. A repository URL below is a **candidate location**, not an approved release pin. M0 checks current maintenance/capability and selects pins; M2 proves the full output contract. Future updates invalidate only the affected parser/query results and support claims.

January 2025 is a compatibility-effort boundary, not a parser switch. Include the relevant modern stable syntax of the admitted toolchain, including post-January-2025 changes that affect these declarations. Older syntax accepted through the same implementation receives incidental support; no separate legacy engine, dialect shim or grammar branch is required. Record unsupported modern constructs individually; an unsupported required core construct blocks that row rather than silently turning its acceptance into file-only reporting.

## 3. Exact fixture and oracle structure

Each stem above owns these files under `tests/fixtures/structural/<stem>/`:

- `input.txt`: independently authored input source and case separators consumed by a test-only fixture decoder.
- `observed.txt`: corresponding edited source, with additions, removals and body-only edits.
- `incomplete.txt`: in-progress/malformed modern source for exact recovery-limit tests.
- `expected.json`: independently reviewed declaration fragments, parameters/result states, matched/unmatched identities and coverage outcomes.
- `cases.json`: explicit case names, virtual filename/dialect, selected source ranges, expected diagnostic, source/specification reference and fixture ownership.

These are test-only textual sources; they are never executed as repository code. C/C++ preprocessor, Rust macro and Zig comptime samples exercise syntax only. A richer directory may be admitted where a language needs separate embedded files; name the additional paths before editing. Do not regenerate `expected.json` from the extractor under test and call that semantic evidence.

For each language, include independently added same-name declarations, signature and body-only changes, unchanged signature with directly changed referenced type, repeated/nested names, explicit absence versus parse failure, defaults that change without exposing literal values, and Unicode/CRLF where relevant. Common cases may share data only when the language's expected syntax and lifetime are independently stated. Examples from an upstream corpus help establish grammar inputs; an upstream successful parse alone does not prove Passeur's extraction or matching.

## 4. Svelte and embedded-source qualification

The inspected Svelte grammar represents some snippet arguments/expressions as raw text. Required extraction must therefore prove more than top-level parse success. Use grammar-identified embedded ranges and qualified JS/TS parsing, with an explicit source map back to original bytes. A small synthetic wrapper is acceptable only if it delegates parsing to the established grammar and its mapping/accepted syntax is tested; it is not an inferred type or expression evaluator. Do not split parameters with commas/regular expressions: defaults and destructuring can contain nested delimiters.

Cover multiple scripts, `lang="ts"`, module context, script text resembling a tag boundary, snippet defaults/destructuring, named render expressions, template-only changes, and `.svelte.js`/`.svelte.ts`. Svelte 5's documented snippet restrictions, such as the absence of rest parameters, are part of the fixture contract; invalid examples must fail as invalid/incomplete rather than become supported syntax. Initial acceptance does not require preprocessors such as arbitrary Pug/CoffeeScript; those receive explicit unsupported-language-region status.

Byte offsets, UTF-16 indices used by bindings, codepoints and line/column positions are separate units. Declare the helper's native convention, convert through one tested owner, and test non-BMP characters preceding and inside an embedded region. Default rendering must never slice the wrong source bytes while claiming a valid declaration.

## 5. Parser backend, packaging and bounded investigation

Initial selection is the official native Node Tree-sitter binding in one helper process. It provides the shared parser interface while per-language grammars/queries own syntax differences. Native code is a dependency-trust/ABI decision, not a promise of sandboxing. The helper boundary isolates parser crashes from the service and keeps synchronous parsing off supervision paths.

M0's finite investigation asks whether the required grammar set can be packaged/load-tested under one selected Node/binding/grammar ABI, including external scanners, with acceptable CPU/RSS. First compare native candidate availability and test representative C++, Odin and Svelte embedded cases. Then record one selected backend and a per-language artifact matrix. Stop the investigation when packaging feasibility, exact identities and the first vertical-path contract are sufficient. Full language correctness belongs to M2; do not perform the entire implementation in M0.

Use the official native Node binding in the service-owned local analysis helper. Each packaged grammar/scanner must load under the admitted Node/runtime ABI and satisfy its exact extraction fixtures. Native source builds are a reviewed artifact-production step, never a runtime download or compilation. A failed native grammar package blocks only that qualification path until resolved; it does not justify silently changing the backend or declaring file-level coverage equivalent to structural support.

Bundle approved artifacts in the installed runtime. Build-time parser generation/toolchains are explicitly provisioned and pinned; their commands may have automatic downloads, which must be controlled by the authorized build procedure. Installed monitoring has no network, npm install, compiler, Tree-sitter CLI or grammar-generation dependency. Updating extraction rules is an independently identifiable change even when grammar bytes remain unchanged.

## Evaluator qualification is a separate claim

All thirteen structural rows remain mandatory and are tested without a decision model. Model judgments never repair extraction fixtures or fill missing syntax. For the assisted objective, the evaluator verification matrix also covers each row's admitted code forms and each applicable question/context tier. Natural-language intent cases are qualified independently from code cases. A language that parses accurately is not thereby proven interpretable by the evaluator.

Source truth, expected declaration fragments and range mapping remain decided by independently reviewed source. Semantic labels come from independently adjudicated coordination scenarios, not from the evaluator, its confidence, or parser output alone. The evaluator manifest names per-row eligibility and explicit out-of-domain forms. Missing applicable semantic evidence blocks that assisted claim without weakening required structural coverage.
