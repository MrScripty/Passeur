# SC16 engineering evidence

Status: **partial engineering evidence; SC16 pending integrated acceptance**. The maintainer specified bounded observation and controlled overload on documented supported environments, available task controls, preserved coding-worker lifetime/ownership, and representative CPU, memory, latency and parent-context measurements. The implementation lead selects limits and configuration. There are no maintainer-approved numeric performance targets to await.

## Limits selected so far

| Limit | Current value and owner | Evidence boundary |
|---|---|---|
| Source capture read ceiling | 8 MiB per source operation in `src/observation/source.ts`; caller may choose a lower `max_bytes` | Existing source tests cover rejection; this does not bound native parser RSS or aggregate caches. |
| Analysis concurrency | One helper child active in `src/observation/helper.ts` | Direct native helper check confirms extraction through a child; service integration remains pending. |
| Waiting analysis jobs | Four waiting jobs in the helper owner | A fifth waiting request is refused with `STRUCTURAL_ANALYSIS_CAPACITY`; close drains waiting jobs. |
| Validated native extraction reuse | At most 16 entries and 8 MiB of serialized extraction data, keyed by captured content, dialect and parser/extractor/build identities | Reused results are rebound to each requesting capture; abort and close still take precedence. Focused real-native cache tests pass 3/3. This bounds the cache, not parser RSS. |
| IPC and reply bytes | 9 MiB request through Node IPC; 1 MiB framed stdout reply in `src/observation/helper-protocol.ts` | The service checks stdout chunks before parsing the reply, and the child checks its serialized reply before sending. Node IPC still deserializes the bounded captured-source request in the child; the Linux child RSS limit is sampled, while a representative public pressure run remains pending. |
| Per-job time | 30 seconds; timeout kills only the analysis child | Direct timeout/saturated-service evidence remains pending. This is not a coding-worker deadline. |
| Retained captured detail | At most 32 pairs and 64 MiB of captured source bytes in the current service process | Eviction/restart yields `STRUCTURAL_DETAIL_UNAVAILABLE`; this is a byte-accounting cap, not a full process RSS cap. |
| Detail response | At most 8192 captured UTF-8 bytes per request | Requires the active work owner and the same work revision; no path re-read. |

The helper now samples Linux child RSS every 100 ms and terminates only the analysis child at a fixed 512 MiB limit, retaining its slot until child close; a one-second termination grace is used. Focused helper-resource tests passed 12/12. The observation store caps artifacts at 16 and 64 MiB and notices at 256; integrated overload behavior remains pending. Analysis overload may defer work or return an explicit incomplete result. These limits apply only to observation jobs, not coding workers, task ownership or task-control admission. A general adaptive resource scheduler is outside this plan.

## Measurements and acceptance

A component benchmark on Linux x64 and Node 24.12.0 used seven workload pairs and three warmed samples: 1.56–1.84 s wall time, parent CPU 211–240 ms, sampled child CPU 1.31–1.75 s, peak parent RSS 117–121 MiB, sampled child RSS 86–92 MiB, and 11,293 compact parent-context bytes per run. Child samples are lower bounds and cgroup counters were unavailable. These measurements cover the native component, not SC16 public or installed acceptance. Measure the final native/public/installed candidate and its feature-disabled baseline on named supported environments and representative corpora using [V15](verification-and-release.md#4-bounded-observation-and-representative-resource-measurements). Include saturated analysis while input, cancel and recovery controls remain usable, and observe actual coding-worker continuation/ownership. Record raw samples, environment, configured limits, overload results and limitations. Do not turn a parser-load or sparse fixture timing into SC16 acceptance.

A development public-path dry run used `scripts/benchmark-structural.ts public` with fresh elected services, the same Git state/corpus, and `PASSEUR_OBSERVATION_MONITOR=off` for the feature-disabled baseline. The corpus included two Passeur TypeScript files plus Rust and Svelte sources. In three rounds, the disabled service's 2-second idle sample showed 96.4 MiB RSS and status/task round trips of 2.27/0.85/0.67 ms. Enabled report latency was about 1.10 seconds; explicit refresh published in about 1.33 seconds. Under a saturated report slot, a second report returned `STRUCTURAL_ANALYSIS_CAPACITY` while sampled task-control reads completed in 2.43/1.36/2.39 ms before the 1.10–1.42-second reports. Enabled peak service RSS was 140.5 MiB and sampled child RSS 96.3 MiB; four report responses totaled 30,875 serialized bytes. Two watcher edits were observed in 1.35/1.38 seconds, and the service RSS increased to 151.6 MiB across that short run, so no memory plateau is claimed. These are development observations from a small mixed corpus; installed baseline, real worker input/cancel/recovery and representative long-run costs remain pending.

An **installed** public-path run used clean build `c0d9cc8e8ead28e736f092f235f826dbe8e95926ccf81e4b2b2ba67f81682f73` from committed source `1f9b64f`, Node 24.12.0 on Linux x64 (24 available CPUs; 66.8 GB host RAM; cgroup limits unavailable). Raw JSON is retained at `/tmp/passeur-sc16-installed-1f9b64f.json`. The same four-path Git corpus and changed bytes were used across fresh monitor-off and enabled service generations, with three saturation samples and two watcher edits. The disabled service's two-second idle peak was 95.8 MB RSS, with control calls 2.72/1.09/1.04 ms. The enabled service sampled 1.09 s parent CPU and 2.19 s child CPU, peak 147.5 MB parent RSS and 120.7 MB child RSS over the short 5.88 s run; its separate two-second idle sample consumed no sampled CPU and peaked at 121.0 MB RSS. An explicit refresh took 1.81 s, the initial report 181 ms, and three saturated analyses took 173–189 ms while control reads took 1.33–2.07 ms and completed first; a second optional analysis returned `STRUCTURAL_ANALYSIS_CAPACITY`. Two body-only edits became current in 534/586 ms without material notices. Serialized parent report context was 30,879 bytes. Child sampling includes Git and native helper processes and is a lower bound; the short run does not establish RSS plateau or active-worker input/cancel/recovery. The installed V13 isolation probe and final candidate may change after fixture-only repair, so this measurement remains engineering evidence until correlated with the final material and live worker run.
