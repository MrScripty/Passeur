# Composed-design admission

**Reviewer:** GPT-6.1 Sol High, read-only architecture planning
**Baseline:** Passeur `6e61bd93e74686620f0cffc3e54bf00c8e5373f8`
**Result:** qualified admission; implementation and acceptance remain open.

1. **Independent concerns — qualified yes.** Registration owns installation/build/catalog policy; each frontend owns its launch context, connection and resolved repository binding; workspace discovery owns canonical Git facts; repository binding owns deterministic profile/state selection; service bootstrap owns repository-scoped election; RepositoryRuntime/coordinator/store retain task and resource authority. A global default belongs in existing profile resolution and must never own the current repository, service or task controller. Optional repository overrides remain possible. Do not promote a repository-specific worktree root blindly into a global profile.
2. **Necessary and accidental interleavings — qualified yes.** Preserve repository ID/state/service generation, task source/owner/execution snapshot, authenticated source view and lifecycle/resource evidence. Remove registration cwd as repository selector, mandatory repository profile setup, named registration as domain identity, inherited Git location variables as identity, stale frontend catalogs as Passeur authority, and service source view as the current frontend source view. Freeze one coherent resolved binding per frontend.
3. **Caller knowledge — yes.** The routine caller needs only one `passeur` registration and ordinary task operations. Repository/profile/state/socket/election details stay internal or diagnostic. Host launch context must be qualified; a host with no context cannot be redirected to a remembered global repository. Task adoption remains distinct from joining the repository service.
4. **Representative change paths — yes.** Adding a repository changes runtime binding only; opening a linked worktree changes source view only; changing the global default changes configuration and requires controlled service cutover; host launch changes touch registration/probe; diagnostic growth touches bounded contracts and projections; dead-service recovery stays in bootstrap; old-registration cleanup stays in the config editor. No global router or scheduler changes are indicated.
5. **Stable interface/hidden knowledge — qualified yes.** Keep LaunchIntent, resolved binding, authenticated source view and private service operations. Expose launch inputs separately from resolved frontend and connected-service facts. Carry bounded diagnostics through schema, transport, service, client, frontend and MCP. Authenticated handshake errors need safe projection; do not leak credentials. Strict IPC evolution needs exact-build conflict checks.
6. **Independent evolution/failure — qualified yes.** A profile/election failure in one repository must not block another. A frontend close removes observation/presentation but does not terminate accepted service-owned work. Qualify with separate processes, including blocked election in repository A while repository B can attach/submit. Investigate generic child-start stderr only if the qualification reproduces a material gap; never retry uncertain mutations automatically.
7. **Deletion test — yes with compatibility narrowing.** Keep the repository service/election guard, per-frontend owner/source view, descriptor/build/generation checks, CLI explicit bindings, Git lease/history/resource protections and deterministic legacy profile lookup for existing consumers. Add a global default inside existing profile ownership. Remove architectural dependency on named registrations. Do not add a global repository map, a second profile registry, a global lock, profile copies, another daemon or another scheduler. Exact cleanup must use config structure and existing ownership/fingerprint protections, never a name-prefix delete.
8. **Complexity — qualified yes.** The smallest coherent change is global profile fallback/provenance, environment-clean repository discovery, complete bounded diagnostics, resolved frontend/service status, compatibility documentation/config cleanup where justified, and claim-matched tests. Existing service/task owners remain the deep modules. Residual complexity is justified by distinct repository domains, task authority, profile cutovers and canonical repository versus source view.

**Conditions:** define global default and override precedence; retain explicit migration for legacy profile schemas; prove actual host launch context through a real host when available; reproduce path/profile/dead-service cases; preserve source/task ownership; reserve real-host sessions and independent final review as separate acceptance gates. This design admission is not acceptance evidence.
