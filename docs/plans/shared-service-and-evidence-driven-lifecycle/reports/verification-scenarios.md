# Claim-matched verification scenarios

This is a procedure specification. **No scenario has been run for the proposed implementation.** Test names and scenario IDs are proposed, not evidence. Existing fixtures may satisfy a selected assertion when they exercise the same actual boundary and oracle.

Use the pinned commands in the examined package: `npm ci`, `npm run check`, `npm test`, `npm run build:runtime`, and the installed-path checks appropriate to the candidate. These commands are supporting gates, not permission to install packages or use credentials. A substituted compiler, dummy module, mock SDK, omitted test, or environment patch must be labelled with its real proof boundary.

Each result records candidate/build, assertion, inputs, authoritative expected result, observed outputs/effects, real versus substituted boundaries, OS/filesystem/native versions, command/procedure, owner, evidence location and retained resources.

## V1 — Concurrent first attachment and stable binding

Start two actual front ends together against one disposable repository and state root. Submit different request keys. Independently observe one elected service process and one native task owner/queue. Repeat through a linked worktree with an explicit shared configuration and validate task-local source views. A conflicting profile meaning/state namespace returns a typed conflict before work; the first client cannot silently redefine it.

Proof: real kernel ownership and process inspection plus actual socket/record effects, not factory call counts. Test short socket-path limits and hostile/symlink candidates under the selected filesystem threat model. A non-Git review directory retains its declared behavior.

## V2 — Live but paused owner

After preparing the service, pause the service process with an authorized test harness. Allow the existing heartbeat threshold to pass, or directly exercise the relevant stale-clock branch while retaining a real kernel lock. Attempt connection/start from another front end. The owner remains elected; no second mutating service starts; no test deletes a lock to make progress. Resume the owner and confirm the original tasks/namespace remain usable.

This is the deciding oracle for retaining a process-lifetime guard in addition to historical cooperative lease handling. A mocked “lock held” result cannot prove it.

## V3 — Election guard release and descriptor lifetime

Crash an idle service; confirm its lock is actually released and a replacement can acquire election without an age-based kill. Retain an unrelated process to prove it is untouched. Verify native worker/Git/proxy descendants did not inherit the election descriptor. Test partial descriptor publication, stale socket, wrong service generation, mismatched protocol/build and permission errors. Only the elected owner may remove its exact stale endpoint.

An inherited descriptor or two competing owners fails acceptance. A wrong build is not repaired by killing it or launching a second service.

## V4 — No task lifetime from time

Use an injected clock at actual owner boundaries to cross former 30-minute task, five-minute approval, ninety-second Git, and queue deadlines. Assert that the durable task state is still active/waiting, the native peer receives no cancel/interrupt/signal, and the original execution ID remains.

Supplement clock tests with real quiet Node peers and a real long-running Git/hook fixture under caller detach/reconnect. The harness itself may have a test safety budget and explicit cleanup; its timeout must not enter production policy. Record that simulated time is not proof of an actual provider tolerating multi-hour work; V13 supplies the live path.

## V5 — Request and client loss

Lose the submitting response before its durable acknowledgment; cancel/timeout a wait; close one stdio client; then close all clients. The task continues under the service; independent clients/tasks do not change outcome. Reconnect through an authorized owner context and retrieve current state or the exact original result. A proxy crash must not signal the service group or its workers.

Check cancellation on each side of admission publication. Before publication, the outcome is either no accepted task or an explicitly uncertain response; after publication, retry finds the same task. No double submission.

## V6 — Identity, authorization, and different worktrees

Test equivalent retries, different agent/intent/base/source-view conflicts, removed/reconfigured agent with retained work, and cross-client coincident keys. Same-user access to one repository does not automatically give another connection input/cancel authority. The explicit human attach/adoption flow increments control generation; stale connections cannot use prior input claims. Lost acknowledgment and service restart preserve records.

Observe actual task worktrees and exact Git OIDs; source review in worktree A must not accidentally read B. Direct edits by caller sessions remain outside Passeur's coordination claim and are documented.

## V7 — Native completion versus waiting

For each adapter feed independently specified native sequences: long silence during a live turn; an outstanding tool/subprocess; multiple tools with one pending; a terminal turn requesting clarification; a genuine completed assignment; nonterminal retries/continuations; missing/ambiguous structured report; and a delayed event from an old generation.

Assert the externally visible distinctions. Complete assignment requires matching native terminal/settlement evidence and accounted obligations. A missing event is not proof of zero outstanding work. No heuristic text parser or extra model is used as the oracle. Persisted worker-report schemas are decoded independently of native terminal classification.

## V8 — Human input lifetime and request association

Through an actual MCP client capable of elicitation, submit then let the original submit call return. Generate a native permission request, read `input_required`, and invoke the dedicated input operation. Verify that the elicitation is associated with that active input tool call and reaches the correct client/human.

Leave it unanswered beyond previous application limits, cancel just the presentation, detach the owner and later explicitly reattach. The task remains pending and the native action remains unapproved. Repeat with ordinary clarification; its answer must never authorize a permission request. Client capability absent or unsupported response variant remains explicit.

## V9 — Input/cancel/completion races

Exercise human allow, human deny, prompt dismissal, host timeout, native withdrawal, repeated same-key reply, conflicting reply, replayed old generation, cancellation before/after completion and two observers asking to present the same prompt. One committed input intent can authorize only its exact native operation. A delivered response to an obsolete request fails.

Inject failure after answer persistence but before native dispatch, after dispatch before acknowledgment, and after native resolution. The service must not blindly resend an uncertain side effect. Independently observe what the native test peer actually received; internal receipt creation alone is insufficient.

## V10 — True native failure and uncertain liveness

Exit the native parent while a child retains stdout; assert prompt detection of parent exit separate from stream closure. Break the transport while leaving the process alive; assert uncertainty instead of fabricated crash or success. Exercise a real nonzero exit, structured terminal error, successful runtime stop after a failed turn, and native protocol corruption.

An unresponsive-but-alive peer remains observable/needs attention; it is not killed by silence. Any failure-triggered cleanup records its actual reason and stop evidence. Prove no unsafe replacement or retirement while descendants remain uncertain.

## V11 — Service crash, publication and Git protection

Crash the service before admission, after durable admission, after start intent, after native startup/submission, during a pending prompt, after native terminal observation, after result write but before terminal-state publication, and during disposition. Use a scoped subset that covers each distinct publication invariant rather than every source line.

Restart under actual guards; compare task/run IDs and retained Git OIDs. No uncertain inference is automatically resubmitted. Known never-started tasks remain explicitly recoverable. Surviving/unknown workers freeze relevant mutation. Simulate process-ID reuse through a controlled process-birth identity source and test the real process boundary where practical. Cleanup must preserve exact named protective refs and refuse dirty/locked/unique work; verify protected OIDs after any accepted removal.

## V12 — Versioned migration and installed artifact

Use representative v1/v2 profiles and v1/v2/v3 results/snapshots. Preserve old bytes and operation receipts, reject corrupt nested facts and unsupported versions, explicitly migrate policy, and reopen new records through the real codecs. Interrupt profile publication and inspect exact backup/candidate outcomes. Old execution tools must not start new workers under changed semantics.

Build/install the exact candidate, hide/remove only the disposable source checkout, and run its front end/service without undeclared development imports. Preserve named startup policy, human-approval rules, deny lists, safe managed/unmanaged edit behavior and project/state binding. An incompatible live service returns a diagnostic; an old writer must not be treated as compatible merely because JSON parses. Rollback after new writes refuses unsafe downgrade.

## V13 — Required-real two-session workflow

On the operator-authorized actual Linux deployment, use two separate Codex sessions against one disposable Git repository. Use authenticated Muse and the supported Codex worker route without credential substitution. Record exact host/native/SDK/build/OS/filesystem versions.

Run one long-horizon assignment and another independent assignment. Observe quiet tool work and genuine progress/terminal events. Close either session, including the original submitter; the other session and accepted work survive. Explicitly reattach, answer human input, test host wait timeout, and request task-specific cancellation. A native completed turn asking for clarification must continue the same assignment after the answer, not generate a duplicate task. Verify native shutdown/descendants independently, ordinary hook/signing behavior, committed or truthful partial delivery, external integration, and explicit resource finalization.

At least one native scenario must exceed the actual formerly failing application limit; retain a repeatable no-inference/controlled-process test for routine regressions. Do not spend allowance merely to produce elapsed time when a qualified native local wait/input path proves the relevant behavior. External runtime/platform-imposed limits are recorded honestly and cannot be hidden behind a Passeur success claim.

Exercise the actual host's Stop behavior and document its distinction from task cancellation. A direct SDK client cannot substitute for host-to-model exposure and human elicitation. If the host terminates independently launched descendants despite process-group separation, re-plan deployment ownership rather than claiming survival.

## V14 — Static, resource and backpressure gates

Run pinned static/application/native/installation checks. Exceed configured admission without spawning work; exceed per-client wait/backlog limits without cancelling healthy native tasks; disconnect slow observers; verify current-state recovery after telemetry omission. Required control/input/terminal state remains durable. Verify that defaults are shared policy, not duplicated constant values and hidden eight-task ceilings.

Search the bounded timer/signal inventory and review each retained timer's owning operation. Search results support source review; absence of a string is not the behavioral proof. Do not add a permanent general-purpose timeout scanner or compliance framework just for this plan.

## V15 — Skills

Validate skill frontmatter, directory names, local links, code/command references and actual tool names. In a fresh session, use the authoring skill to complete/qualify the second adapter. Include cases for another model through an existing adapter, native completed-turn clarification, no heartbeat progress guarantee, missing host input capability, native automatic request resolution, and an unavailable optional SDK that must not hide Passeur's catalog.

Save the resulting dossier, changes and evidence. Structural validation is not the same as successful skill use. Use the usage skill to retrieve a task after lost submit acknowledgment and to explicitly cancel a worker instead of repeatedly cancelling its waits.

## V16 — Review and resource closure

At the complete candidate boundary, obtain independent external review of the actual source and selected evidence. Record findings and dispositions, then rerun changed claims. Confirm the final PR/integration authority and the current material subject. Evidence-only edits do not force an unrelated full review cycle.

Record every plan-created worktree/branch path, exact head/protection/disposition and final state. Unrelated user resources are untouched. A missing required native/review environment leaves the relevant claim blocked; it does not turn into an advisory success.
