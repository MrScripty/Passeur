# Profile and connection ownership inventory

| State or contract | Current owner | Final scope and qualification |
| --- | --- | --- |
| Global Codex registration | `src/codex/config.ts`, invoked by `src/cli.ts` | One unpinned registration inherits the host launch cwd. Its writer establishes a usable installation default before publishing it. |
| Existing Codex registration/profile sources | Parsed TOML and `src/codex/profile-migration.ts` | Only structurally verified managed pinned entries and a bounded supported profile directory are candidates. Sources are preserved. One effective group migrates; ambiguity refuses without changing the old registration. |
| Candidate profile selection | `resolveRepositoryBinding()` in `src/core/repository-runtime.ts` | Explicit, repository, supported legacy, then installation default remains the startup/offline precedence. An unpinned frontend joining a live service does not read a prospective candidate. |
| Profile file contents | `RepositoryRuntime.profileSnapshot()` and `src/core/profile.ts` | Each service generation retains one detached, frozen decoded profile. Catalog and execution use that same snapshot. Loading is config-only and failed loads retry. |
| Effective profile identity | `effectiveProfileFingerprint()` in `src/core/profile.ts`; descriptor and service contract | Versioned fingerprint covers canonical decoded execution/registry configuration and excludes path/provenance. Same content at different paths joins; changed content at a path conflicts against the retained generation. |
| Profile provenance | Runtime snapshot, descriptor and bounded diagnostics | Source path remains available for diagnostics/status where authorized; pathname is not an unpinned service identity key. |
| Repository/state/service domain | Canonical repository ID, state namespace, service generation, bootstrap descriptor/guard/socket | Resolved independently per frontend. Service election remains under the repository guard and unrelated repositories stay independent. |
| Worktree/source view | Frontend project path and authenticated peer source view | Remains distinct from canonical repository identity; each linked worktree shares coordination and presents its own source view. |
| Service build/contract compatibility | Descriptor `runtime.build_id`, `passeur-service-v2`, exact qualified prior build bridge | Build remains diagnostic; modern contract is explicit. Legacy wire behavior is allowed only for the actual qualified installed prior build. Unknown services are controlled conflicts. |
| Frontend principal/task control | Private owner token and peer authentication | Separate for every frontend/session. Connection and catalog access do not adopt tasks. Human-confirmed attach remains the explicit control-transfer path. |
| Agent catalog | Connected `RepositoryRuntime.agents()` or prospective runtime after verified service absence | A live repository service owns the catalog. Offline discovery loads the prospective profile without inference, service start, lease preparation or task-control changes. |
| Accepted work/resources | Service runtime/store/coordinator | Service owns accepted tasks after the submitting frontend exits; profile migration and compatible attachment do not terminate or transfer that work. |
| Error/status projections | Typed bounded runtime/service contracts, client, MCP layer and startup bootstrap | Stage/path/native code/next action and requested/service effective profile identities survive supported boundaries; secrets remain redacted and output bounded. |
